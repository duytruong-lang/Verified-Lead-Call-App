# Team access backend

`team_members` is the canonical team roster. `profiles` mirrors the active role and status used by existing workspace RPCs and RLS. Both rows must match the authenticated Auth user and normalized email; a missing or inconsistent profile/roster denies business access. The `team-admin` Edge Function is the only public route for roster changes. Its `get-session` operation is available to any authenticated identity so the app can explain pending or disabled access; all other team operations require an active admin.

Invitations are created manually through Auth `generateLink`; the function does not send mail. The returned app callback contains Auth's `token_hash` and invite/recovery type. Treat the full link as a bearer credential and hand it to the intended person through the operator's approved channel. The database stores only AES-GCM ciphertext for the token hash, and audit events store only the action kind. Configure `TEAM_LINK_ENCRYPTION_KEY` as a stable server-only secret and set `TEAM_LINK_TTL_SECONDS` to the same lifetime as Supabase Auth's email OTP expiry. Local setup preserves these values in the ignored `.supabase/functions.env`; do not rotate the encryption key while unexpired links remain stored.

A repeated request with the same idempotency key returns the same member and action link while it is valid. If Auth may have generated a link but its response was lost, the backend blocks another Auth token generation until the configured expiry plus a one-minute buffer. During that window, the operator should retry with the same request key; if the backend reports an uncertain link, wait until expiry and then issue a new link with a new key. A newer successful link replaces the old one. No email provider or SMTP credentials are needed for this pilot.

The function returns `LINK_EXPIRED` when that request's link has expired and `LINK_REPLACED` when a newer issuance has superseded its result. These are definitive stale-key responses: the UI may clear that issuance key and require an explicit operator action to create a new link. `member_link_in_progress` and `member_link_uncertain` remain retry/wait states; clients must preserve their original key and must not silently issue another Auth token.

Pending members become active only after a verified Auth session and `complete-onboarding` sets their password server-side. If an invite was verified but the session was lost before password setup, issuing another pending-invite link uses an Auth recovery token while retaining the pending invitation flow; the encrypted retry payload preserves the actual token type. Auth password updates revoke the prior verification session, so sign in again with the new password after onboarding. The activation RPC checks the bound Auth user, normalized email, invitation timestamp, and confirmed email. Active members can use a recovery link to set a new password; disabled members are denied by all business Edge/RPC/RLS paths. Re-enabling a previously activated disabled account preserves its existing Auth identity and history.

Disabling a member or changing them to Viewer prevents new business writes and transactionally cancels their draft attempts, releases their claims, and leaves completed history and attempt counts unchanged. Role/status writes use expected roster versions and idempotency keys. The database serializes admin mutations, rejects self-demotion/self-disable, and preserves a matching active admin even under concurrent changes. Existing recordings, completed attempts, and public share links are retained.

For a fresh local-only project, start Supabase and apply migrations before creating the first team admin. Then run `node scripts/bootstrap-local-admin.mjs admin@example.invalid` with a synthetic/local email. The script refuses non-loopback endpoints and refuses to elevate an existing non-admin identity. A newly generated local password is written with mode `0600` to ignored `.supabase/local-admin-credentials.json`; it is never printed. To run the synthetic authorization and workflow harness, prepare the Edge environment with `node scripts/prepare-local-functions-env.mjs`, serve Edge Functions, then run `node scripts/local-backend-check.mjs`. The harness refuses to run if local leads, mappings, or sync jobs already exist; it never resets a database. It leaves active `admin-keeper` and `staff-a` credentials plus tagged IDs in the ignored `.supabase/backend-test-users.json` manifest for browser checks. After browser tests, run `node scripts/cleanup-local-backend-check.mjs` to remove only manifest-tracked business fixtures and disable only those tagged test identities; it retains Auth/audit history. Then bootstrap the desired local admin. These scripts never target cloud services.
